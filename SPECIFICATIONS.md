# WBR Presbyterian Church CMS -- Technical Specification

## 1. Overview

### 1.1 Project Summary

A Content Management System for a Presbyterian church that manages three core domains: church events (with calendar display), image galleries (hosted on Cloudinary), and church member records (for administrative use). All content is publicly viewable, while all create/update/delete operations are restricted to authenticated administrators.

### 1.3 Key Architectural Decisions

**Authentication**: Use the Rails 8.1 built-in authentication generator (`bin/rails generate authentication`) instead of Devise. This creates `User` and `Session` models, `SessionsController`, `PasswordsController`, and the `Authentication` concern with `require_authentication` and `allow_unauthenticated_access` helpers. Simpler, fewer dependencies, well-integrated with Rails 8.1.

**Image Storage**: Use the `cloudinary` gem directly with a custom `Image` model rather than Active Storage with a Cloudinary adapter. Rationale:

- The admin must browse and select from _previously uploaded_ images when associating them with events or assigning them to galleries. Active Storage is designed around attaching blobs to specific records on upload, not for maintaining a persistent, browsable media library.
- A custom `Image` model stores the Cloudinary `public_id`, `url`, `width`, `height`, `format`, and `bytes`, allowing queries, thumbnails, and gallery ordering without round-tripping to the Cloudinary API.
- Direct use of the `cloudinary` gem gives full access to Cloudinary's URL-based transformation API.

**Event Categories**: Implemented as a string column with a constant-based inclusion validation on the `Event` model. The fixed set (Education, Fellowship, Meetings, Community Service) is defined as a constant. No separate `Category` model. String values are more readable in queries and the database than integer enums.

**Calendar**: Server-rendered monthly grid using Tailwind CSS utility classes, with Turbo Frame wrapping for month-to-month navigation without full page reloads. No JavaScript calendar library.

**Drag-and-Drop Reordering**: SortableJS loaded via import map, wrapped in a Stimulus controller. Gallery image positions are persisted via a `position` integer column on the `GalleryImage` join model.

## 3. Authentication & Authorization

### 3.1 Authentication Generator

Run `bin/rails generate authentication` which produces:

- `app/models/user.rb` -- User model with `has_secure_password`
- `app/models/session.rb` -- Session model
- `app/models/current.rb` -- `Current` singleton (`Current.user`, `Current.session`)
- `app/controllers/sessions_controller.rb` -- Login/logout
- `app/controllers/passwords_controller.rb` -- Password reset flow
- `app/controllers/concerns/authentication.rb` -- The `Authentication` concern
- Migration files for `users` and `sessions`
- View templates for login and password reset

**Prerequisite:** Uncomment `gem "bcrypt", "~> 3.1.7"` in the Gemfile and run `bundle install` before running the generator.

### 3.2 How It Works

The `Authentication` concern mixed into `ApplicationController` provides:

- `require_authentication` -- a `before_action` that redirects unauthenticated users to the login page. All actions require authentication by default.
- `allow_unauthenticated_access` -- a class-level method that skips the auth check for specified actions.
- `authenticated?` -- a boolean helper for conditional rendering in views.

### 3.3 Authorization Strategy

Binary model: logged in = admin, not logged in = public visitor. No roles needed.

**Controller-level pattern:**

```ruby
# Mixed public/admin (e.g., EventsController):
class EventsController < ApplicationController
  allow_unauthenticated_access only: [:index, :show]
end

# Admin-only (e.g., MembersController):
class MembersController < ApplicationController
  # All actions require auth by default
end
```

**View-level pattern:**

```erb
<% if authenticated? %>
  <%= link_to "Edit", edit_event_path(@event) %>
<% end %>
```

### 3.4 Initial Admin User

Created via seed data in `db/seeds.rb`:

```ruby
User.find_or_create_by!(email_address: "admin@example.com") do |user|
  user.password = "changeme123"
  user.password_confirmation = "changeme123"
end
```

## 4. Routes

```ruby
Rails.application.routes.draw do
  # Authentication (generated)
  resource  :session,   only: [:new, :create, :destroy]
  resources :passwords, param: :token, only: [:new, :create, :edit, :update]

  # Events (public index/show, admin CRUD)
  resources :events

  # Galleries (public index/show, admin CRUD + reorder)
  resources :galleries do
    patch :reorder, on: :member
  end

  # Calendar (public)
  get "calendar", to: "calendar#show", as: :calendar

  # Members (admin only)
  resources :members

  # Image management (admin only)
  namespace :admin do
    resources :images, only: [:index, :new, :create, :destroy]
  end

  # Homepage
  root "pages#home"

  # Health check (existing)
  get "up" => "rails/health#show", as: :rails_health_check
end
```

## 5. Controllers

### 5.1 PagesController

- `home` -- Queries `Event.this_week.includes(:image)` and `Member.birthdays_this_month`.
- Auth: `allow_unauthenticated_access`

### 5.2 EventsController

- Full CRUD: `index`, `show`, `new`, `create`, `edit`, `update`, `destroy`
- `index` supports optional `category` filter param. Eager-loads images.
- `new`/`edit` load `Image.all` for image selector.
- Auth: `allow_unauthenticated_access only: [:index, :show]`
- Strong params: `params.expect(event: [:title, :description, :event_date, :start_time, :end_time, :location, :category, :image_id])`

### 5.3 CalendarController

- `show` -- Accepts optional `month`, `year`, and `category` params. Defaults to current month. Queries `Event.for_month(date).by_category(category).includes(:image)`. Groups by date.
- Response wrapped in Turbo Frame for month navigation.
- Auth: `allow_unauthenticated_access`

### 5.4 GalleriesController

- Full CRUD plus `reorder`
- `index` -- Public visitors see only `Gallery.published`; authenticated users see all.
- `show` -- Displays gallery with ordered images.
- `edit` -- Loads `Image.all` for image picker and current ordered images.
- `update` -- Accepts `image_ids: []` to sync assignments.
- `reorder` -- Accepts `{ ordered_ids: [...] }`, updates positions in a transaction.
- Auth: `allow_unauthenticated_access only: [:index, :show]`

### 5.5 Admin::ImagesController

- `index` -- Lists all uploaded images with thumbnails.
- `new` -- Upload form.
- `create` -- Sends file to Cloudinary, stores metadata in `Image` model.
- `destroy` -- Removes from Cloudinary and database.
- Auth: All actions require authentication.

### 5.6 MembersController

- Full CRUD: `index`, `show`, `new`, `create`, `edit`, `update`, `destroy`
- `index` lists members alphabetically.
- Auth: All actions require authentication.
- Strong params: `params.expect(member: [:first_name, :last_name, :email, :phone, :address_line1, :address_line2, :city, :state, :zip_code, :date_of_birth])`

### 5.7 SessionsController and PasswordsController

Generated by `bin/rails generate authentication`. No customization needed.

## 7. Image Management -- Cloudinary Integration

### 7.1 Gem Setup

Add to Gemfile:

```ruby
gem "cloudinary", "~> 2.0"
```

### 7.2 Configuration

**Initializer** (`config/initializers/cloudinary.rb`):

```ruby
Cloudinary.config do |config|
  config.cloud_name = Rails.application.credentials.dig(:cloudinary, :cloud_name)
  config.api_key    = Rails.application.credentials.dig(:cloudinary, :api_key)
  config.api_secret = Rails.application.credentials.dig(:cloudinary, :api_secret)
  config.secure     = true
end
```

**Rails credentials** (`bin/rails credentials:edit`):

```yaml
cloudinary:
  cloud_name: your_cloud_name
  api_key: '123456789012345'
  api_secret: 'abcdefghijklmnop'
```

### 7.3 Upload Flow

1. Admin navigates to `/admin/images/new`
2. Admin selects a file via standard file input
3. Form submits to `Admin::ImagesController#create`
4. Controller calls `Cloudinary::Uploader.upload(params[:file], folder: "wbr-pres-cms", resource_type: "image", allowed_formats: %w[jpg jpeg png webp gif])`
5. Cloudinary returns metadata: `public_id`, `secure_url`, `width`, `height`, `format`, `bytes`
6. Controller creates `Image` record with these attributes
7. Redirect to `admin_images_path` with success flash

### 7.4 Image Deletion

1. Check if image is assigned to any events -- warn if so
2. Call `Cloudinary::Uploader.destroy(image.cloudinary_public_id)`
3. Delete `Image` record (cascades to `gallery_images`; nullifies `events.image_id`)

## 8. Calendar View

### 8.1 Technical Approach

Server-rendered HTML grid using a 7-column CSS grid with Tailwind. Month navigation uses a Turbo Frame so only the calendar grid is replaced on prev/next clicks.

### 8.2 Controller Logic

```ruby
class CalendarController < ApplicationController
  allow_unauthenticated_access

  def show
    @date = parse_date_params
    @category = params[:category]
    @events = Event.for_month(@date).by_category(@category).includes(:image)
    @events_by_date = @events.group_by(&:event_date)
  end

  private

  def parse_date_params
    if params[:month].present? && params[:year].present?
      Date.new(params[:year].to_i, params[:month].to_i, 1)
    else
      Date.current
    end
  end
end
```

## 10. Helper Methods

### 10.1 ApplicationHelper -- Ordinal Date Formatting

```ruby
module ApplicationHelper
  def ordinalize_day(date)
    date.day.ordinalize
  end

  # "February 5th"
  def month_day_ordinal(date)
    "#{date.strftime('%B')} #{ordinalize_day(date)}"
  end

  # "Wednesday, February 19th"
  def full_date_ordinal(date)
    "#{date.strftime('%A')}, #{month_day_ordinal(date)}"
  end

  # "Wednesday, February 19th, 2026"
  def full_date_ordinal_with_year(date)
    "#{full_date_ordinal(date)}, #{date.year}"
  end

  def format_time(time)
    time&.strftime("%-I:%M %p")
  end

  # "10:00 AM - 11:30 AM" or "10:00 AM"
  def event_time_range(event)
    start = format_time(event.start_time)
    event.end_time.present? ? "#{start} - #{format_time(event.end_time)}" : start
  end
end
```

### 13.1 Hosting Overview

| Rails App (web)    | Usage-based   | CPU + memory consumed per second              |

| Builds             | $0            | Included in plan                              |

For a low-traffic church site, the $5 in included credits should cover most or all usage. If usage exceeds the included credits, you pay only for the overage.

### 13.2 Prerequisites

1. A GitHub account (Railway connects directly to your repo)
2. The Railway CLI (optional but useful): `npm install -g @railway/cli`
3. Your code pushed to a GitHub repository

### 13.3 One-Time Setup

#### Step 1: Create a Railway Account and Project

1. Sign up at [railway.com](https://railway.com/) using your GitHub account
2. Select the **Hobby** plan ($5/month)
3. Click **New Project** > **Deploy from GitHub repo**
4. Select your `wbr-pres-cms` repository
5. Railway will auto-detect the Dockerfile and begin building

#### Step 2: Add a PostgreSQL Database

1. In your Railway project dashboard, click **New** > **Database** > **PostgreSQL**
2. Railway provisions the database service

**Important:** Railway does NOT automatically inject a resolved `DATABASE_URL` into your web service. The Postgres service's `DATABASE_URL` variable is itself a template string (e.g., `postgresql://${{PGUSER}}:...`) that does not resolve when cross-referenced between services. You must manually construct the `DATABASE_URL` in your web service using the actual values from the Postgres service's Variables tab.

#### Step 3: Set Environment Variables

In the Railway dashboard, go to your web service > **Variables** and add:

| Variable                   | Value                           | Notes                                       |
| -------------------------- | ------------------------------- | ------------------------------------------- |
| `DATABASE_URL`             | See construction guide below    | Must be manually set — see note             |
| `RAILS_MASTER_KEY`         | Contents of `config/master.key` | Copy the key value, not the file path       |
| `RAILS_ENV`                | `production`                    |                                             |
| `RAILS_SERVE_STATIC_FILES` | `true`                          | Railway doesn't use a separate web server   |
| `SOLID_QUEUE_IN_PUMA`      | `true`                          | Runs background jobs inside the web process |

**Constructing `DATABASE_URL` manually:**

Railway's cross-service `${{Postgres.DATABASE_URL}}` reference does not work because that variable is itself a template. Instead, go to the Postgres service → Variables tab and find the literal values for `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, and the TCP proxy domain/port (`RAILWAY_TCP_PROXY_DOMAIN`, `RAILWAY_TCP_PROXY_PORT`). Then set `DATABASE_URL` in the web service to:

```
postgresql://postgres:<POSTGRES_PASSWORD>@<RAILWAY_TCP_PROXY_DOMAIN>:<RAILWAY_TCP_PROXY_PORT>/railway
```

Alternatively, enable **Private Networking** in Railway project settings and use the `.railway.internal` hostname.

Cloudinary credentials are stored in Rails encrypted credentials (`bin/rails credentials:edit`), which are decrypted at runtime using `RAILS_MASTER_KEY`. No need to set them as separate environment variables.

#### Step 4: Configure `config/database.yml` for Production

Rails automatically uses `DATABASE_URL` when it's present in the environment, which overrides the `database.yml` settings. However, for the auxiliary databases (cache, queue, cable) that use Solid adapters, update the production config to use the same database:

```yaml
production:
  primary:
    <<: *default
    url: <%= ENV["DATABASE_URL"] %>
  cache:
    <<: *default
    url: <%= ENV["DATABASE_URL"] %>
    migrations_paths: db/cache_migrate
  queue:
    <<: *default
    url: <%= ENV["DATABASE_URL"] %>
    migrations_paths: db/queue_migrate
  cable:
    <<: *default
    url: <%= ENV["DATABASE_URL"] %>
    migrations_paths: db/cable_migrate
```

This consolidates all databases into the single PostgreSQL instance provided by Railway, keeping costs down.

#### Step 5: Enable SSL in Production

In `config/environments/production.rb`, uncomment or add:

```ruby
config.assume_ssl = true
config.force_ssl = true
```

#### Step 6: Configure Custom Domain (Optional)

1. In the Railway dashboard, go to your web service > **Settings** > **Networking**
2. Add your custom domain (e.g., `cms.yourchurch.org`)
3. Railway provides the DNS records to add at your domain registrar
4. SSL is provisioned automatically once DNS propagates

Without a custom domain, Railway provides a free `*.up.railway.app` URL.

### 13.4 How Railway Builds the App

Railway detects the `Dockerfile` in the project root and uses it to build the application. The existing multi-stage Dockerfile already handles:

- Installing Ruby and dependencies
- Running `bundle install`
- Precompiling assets (Tailwind CSS + import maps)
- Setting up Thruster for HTTP compression

Railway runs the container using the `CMD` from the Dockerfile (`./bin/thrust ./bin/rails server`). The `bin/docker-entrypoint` script automatically runs `db:prepare` on startup, which creates and migrates the database.
